# 从 SparkFlow V2 到动态专家团队

这是一份面向 SparkFlow 的智能体工程入门教程。读完以后，你应该能够看懂当前 Trading Team V2 的执行过程，判断一个功能属于提示词、工具、工作流还是数据工程，并且能和我一起设计下一版动态专家团队。

教程不要求你先成为机器学习工程师。你需要能够阅读基础的 TypeScript、Python 和 JSON，知道 HTTP API 大致怎样工作，并愿意沿着一次真实任务把问题拆开。

## 学完以后能做什么

你将能够完成下面这些事情。

1. 解释普通模型调用、工具型智能体和多智能体系统的差别。
2. 看懂 SparkFlow 如何识别 `AAPL v2` 并启动 Vibe-Trading。
3. 看懂专家之间为什么要用 DAG 传递结果。
4. 为一个专家写清能力、工具权限、输入和输出。
5. 设计统一证据包，减少重复抓取和数据冲突。
6. 让主管从专家池中选择合适成员并生成合法执行计划。
7. 判断什么时候应该追加专家，什么时候应该停止分析。
8. 为智能体系统设计成本限制、失败恢复和评测样本。

最终练习是一份 `Trading Team V3` 设计。V3 收到研究问题以后，会自行选择四至八名专家，完成分析并给出唯一结论。

## 先认识你手里的项目

SparkFlow 现在已经具备一套可用的多智能体基础设施。

前端在 [`MacroAiAnalyst.tsx`](../../src/components/MacroAiAnalyst.tsx) 中识别个股输入。普通代码走原版研究流程，带有 `v2` 后缀的输入会调用 [`buildTradingTeamV2Prompt`](../../src/lib/marketResearchPrompts.ts)。

Vibe-Trading 收到请求以后调用 `run_swarm`。当前固定团队定义在 [`trading_analysis_team_v2.yaml`](../../services/vibe-trading/agent/src/swarm/presets/trading_analysis_team_v2.yaml) 中。这个文件声明了十二名执行专家、每名专家可用的工具、任务依赖和最终报告要求。

真正执行任务的部分位于 Vibe-Trading 的 Swarm 模块。

- [`models.py`](../../services/vibe-trading/agent/src/swarm/models.py) 定义 Agent、Task 和 Run 的数据结构。
- [`presets.py`](../../services/vibe-trading/agent/src/swarm/presets.py) 读取 YAML 并检查 DAG。
- [`runtime.py`](../../services/vibe-trading/agent/src/swarm/runtime.py) 按拓扑层执行任务，同一层可以并行。
- [`worker.py`](../../services/vibe-trading/agent/src/swarm/worker.py) 给单个专家加载模型、工具、上游结论和执行规则。
- [`swarm_tool.py`](../../services/vibe-trading/agent/src/tools/swarm_tool.py) 负责选择预设、提取变量并等待结果。

先记住一条主线。

```text
页面输入
  ↓
研究请求
  ↓
任务计划
  ↓
专家执行
  ↓
证据与结论交接
  ↓
最终裁决
  ↓
Markdown 报告
```

智能体系统的大部分问题，都能在这条主线上找到位置。

## 第一课 模型调用和智能体有什么不同

最简单的模型调用只有输入和输出。

```ts
const answer = await model.generate(prompt)
```

模型看到问题以后直接写答案。它无法确认最新股价，也不知道项目里有哪些数据工具。提示词写得再长，也不会凭空获得实时数据。

工具型智能体多了一个执行循环。

```text
读取问题
  ↓
决定需要什么数据
  ↓
调用工具
  ↓
读取工具结果
  ↓
继续调用或输出答案
```

多智能体系统又多了一层任务分工。一名主管把问题拆成多个任务，不同专家分别完成，再由后续角色处理分歧和裁决。

判断一个系统有没有真正进入智能体工程，可以看三个信号。

1. 模型能否选择并调用外部工具。
2. 一次任务能否经历多个有状态的步骤。
3. 每一步的输入、输出和失败结果能否被程序检查。

只用一段长提示词生成研报，依然属于单次生成。V2 的四名取证专家会实际调用行情、文件和网页工具，Swarm Runtime 会保存任务状态，因此它已经属于多智能体工作流。

### 本课练习

打开 [`marketResearchPrompts.ts`](../../src/lib/marketResearchPrompts.ts)，找到普通个股研究和 V2 研究的两个 Prompt Builder。回答下面三个问题。

1. 哪个流程希望单个会话直接生成最终报告。
2. 哪个流程要求调用 `run_swarm`。
3. 如果主 Agent 没有调用工具，两个流程分别会发生什么。

完成标准是能够用自己的话解释 Prompt 和 Runtime 各自负责什么。

## 第二课 Tool Calling 怎样工作

Tool Calling 可以理解成模型提交一张结构化申请单。模型不直接执行 Python、抓网页或访问数据库。它只选择工具并给出参数，宿主程序负责真正执行。

一份工具定义通常包含名称、用途和参数 Schema。

```json
{
  "name": "get_market_data",
  "description": "读取证券的 OHLCV 行情",
  "parameters": {
    "type": "object",
    "properties": {
      "symbol": { "type": "string" },
      "period": { "type": "string" }
    },
    "required": ["symbol"]
  }
}
```

模型可能返回下面的调用意图。

```json
{
  "tool": "get_market_data",
  "arguments": {
    "symbol": "AAPL",
    "period": "1y"
  }
}
```

宿主程序验证参数以后执行工具，再把结果交还模型。模型只能相信本轮工具结果、可信证据包或经过标记的上游结论。

工具权限应当按角色分配。新闻专家可以读取网页，报告主编通常不需要重新访问任意网页。这样既控制成本，也降低提示词注入和数据口径漂移的风险。

当前 V2 在 YAML 的每名 Agent 下声明 `tools` 和 `skills`。`worker.py` 会按白名单组装工具注册表。声明了 `get_market_data` 的角色还会收到行情工具使用规则。

### 本课练习

在 V2 YAML 中比较市场分析师和最终风险主管。

- 记录两人的工具列表。
- 解释最终风险主管为什么没有 `get_market_data`。
- 写出一种最终风险主管确实需要补充数据的情况。
- 决定这时应该给主管新增工具，还是把任务退回取证专家。

推荐答案倾向于退回取证专家。最终裁决者直接抓取新数据会绕过前面的证据审查。

## 第三课 专家能力不能只写成角色扮演

一句“你是世界顶级基本面分析师”无法形成稳定能力。一个可用专家至少需要五部分。

| 部分 | 解决的问题 |
|---|---|
| 角色边界 | 专家负责什么，不负责什么 |
| 分析步骤 | 收到任务以后按什么顺序工作 |
| 工具权限 | 可以取得哪些真实数据 |
| 输入输出协议 | 上下游怎样稳定读取结果 |
| 专项评测 | 怎样证明专家真的完成了任务 |

可以把专家定义成下面的结构。

```ts
type AgentCapability = {
  id: string
  displayName: string
  capabilities: string[]
  supportedMarkets: string[]
  tools: string[]
  requiredInputs: string[]
  outputSchema: string
  estimatedCost: number
  timeoutSeconds: number
}
```

基本面专家的 `capabilities` 可以包括财务报表、盈利质量、同业比较和估值。新闻专家则包括事件聚类、来源优先级、重复新闻合并和影响传导。

能力标签用于主管选人。工具权限用于 Runtime 限制行为。输出 Schema 用于程序检查结果。三者不能混在一段自然语言里。

### 本课练习

给“半导体产业链专家”写一份一页纸定义，至少包含下面内容。

1. 能回答的三个问题。
2. 明确拒绝的两个问题。
3. 需要的四类数据。
4. 可以使用的工具。
5. 输出必须包含的字段。
6. 两个失败样本。

完成标准是另一个开发者只看这份定义，就能判断主管什么时候应该选择该专家。

## 第四课 统一证据包

多智能体最常见的浪费，是每个专家重新查询相同数据。更麻烦的情况是，专家分别查到不同时间、不同币种或不同复权口径的数据，最后却把数字放进同一张表。

动态团队应该先运行统一数据预检，生成 `EvidenceBundle`。

```ts
type EvidenceBundle = {
  security: {
    name: string
    ticker: string
    exchange: string
    currency: string
  }
  cutoff: string
  quote?: MarketQuote
  priceSeries?: PriceBar[]
  filings: EvidenceItem[]
  newsEvents: EvidenceItem[]
  fundamentals?: FundamentalSnapshot
  provenance: EvidenceSource[]
  gaps: DataGap[]
}
```

每个证据对象应当保存来源、发布日期、抓取时间、数据期、单位、币种和校验状态。专家引用结论时使用 `evidenceId`，最终报告再把这些编号转换成链接和脚注。

统一证据包还有一个实际好处。主管可以在调用昂贵模型以前判断数据是否足够。证券身份无法确认、行情过期或财报缺失时，系统可以先补数据，避免十二名专家一起分析错误对象。

### 本课练习

为 AAPL 设计一份最小证据包。不要填具体数字，只列字段和来源类型。随后回答下面的问题。

- 价格使用未复权还是复权口径。
- 财务表使用财年还是滚动十二个月。
- 新闻按文章发布时间还是事件发生时间排序。
- 同业数据怎样统一币种和报告期。
- 哪些字段缺失时应该阻止估值专家运行。

## 第五课 DAG 和并行执行

DAG 是有向无环图。每个节点代表任务，每条边代表依赖。没有依赖的任务可以同时运行，依赖未完成的任务必须等待。

V2 的执行关系可以简化成下面这张图。

```text
市场 ─────┐
基本面 ───┼→ 多头 → 空头 → 研究主管 → 交易员 ─┬→ 激进风控 ─┐
新闻 ─────┤                                  ├→ 保守风控 ─┼→ 最终裁决
情绪 ─────┘                                  └→ 中性风控 ─┘
```

四名取证专家位于第一层，可以并行。空头专家需要阅读多头观点，因此排在多头以后。三名风险专家彼此独立，应当在同一层并行。最终主管等待三份风险意见全部完成。

一个合法 DAG 至少要通过四项检查。

1. 每个任务引用的 Agent 必须存在。
2. 每个依赖任务必须存在。
3. 图中不能出现循环。
4. `input_from` 引用的任务必须位于上游。

Vibe-Trading 的 `inspect_preset` 已经能检查这些问题。当前 V2 校验结果包含十二个 Agent、十二个任务和七个拓扑层。

### 本课练习

尝试在纸上设计一条错误依赖，让研究主管依赖最终风险主管，再观察为什么形成循环。随后设计一个财报事件分析 DAG，限制在六名专家以内。

完成标准是能够判断哪些任务可以并行，哪些任务必须串行。

## 第六课 主管怎样智能选人

主管的第一份输出应该是任务计划，不应直接写研究结论。任务计划使用固定 JSON Schema，让后端能够校验。

```ts
type AnalysisPlan = {
  target: string
  market: string
  questionType: string
  horizon: string
  selectedAgents: string[]
  tasks: PlannedTask[]
  requiredEvidence: string[]
  stopConditions: string[]
  budget: {
    maxAgents: number
    maxRounds: number
    maxEstimatedCost: number
  }
  planSummary: string
}
```

主管收到的问题可能是“英伟达财报后还能买吗”。它应当识别证券、财报事件、研究周期和用户真正关心的决策，再从能力注册表中选择专家。

一份合理计划可能选择基本面、预期修正、新闻、市场技术、多头或空头质询、风险主管。它不一定需要完整的宏观、地缘和长期行业专家。

选人过程适合使用规则和模型共同完成。

系统规则先规定最低要求。

- 所有个股研究必须完成证券身份确认。
- 涉及买卖判断必须经过独立风险审查。
- 涉及当前价格必须包含新鲜行情。
- 涉及估值必须有基本面证据。
- 涉及重大事件必须核对原始公告或可靠来源。

主管在这些限制内补充专家、安排依赖和分配预算。后端验证计划，不合格就要求主管修正。

### 本课练习

分别为下面四个问题选择专家，并写出选择理由。

1. 贵州茅台适合持有五年吗。
2. 特斯拉交付数据发布后应该怎样观察。
3. 一家生物科技公司临床三期失败会怎样影响估值。
4. 美联储意外加息对高估值芯片股有什么影响。

每个任务最多选择六名专家。相同问题若总是选满六名，说明能力标签或选择规则仍然太粗。

## 第七课 动态计划怎样变成可执行任务

主管输出的 JSON 还不能直接执行。`DynamicDagCompiler` 需要把计划转换成 `SwarmRun`。

编译过程可以分成六步。

1. 从注册表读取 Agent 定义。
2. 检查所选 Agent 的市场支持和工具权限。
3. 为每个计划任务生成 `SwarmTask`。
4. 补齐系统强制任务和依赖。
5. 检查 DAG、预算、超时和最大并行数。
6. 固化计划版本并启动 Runtime。

伪代码如下。

```python
def compile_plan(plan, registry, evidence_bundle):
    validate_plan_schema(plan)
    agents = registry.resolve(plan.selected_agents)
    tasks = build_tasks(plan.tasks, agents)
    tasks = apply_mandatory_risk_review(tasks)
    validate_capabilities(agents, evidence_bundle)
    validate_dag(tasks)
    validate_budget(plan.budget, agents)
    return SwarmRun(agents=agents, tasks=tasks)
```

编译器属于确定性程序。它不应该依靠另一次模型调用来判断循环依赖、预算超限或未知 Agent。

### 本课练习

给计划验证器写十条规则。至少覆盖未知 Agent、循环依赖、超预算、缺少风险审查、市场不支持、证据过期和重复任务。

## 第八课 什么时候追加专家

第一轮完成以后，主管可以运行一次 Gap Review。它只判断证据是否足够，不重新写整份报告。

```ts
type GapReview = {
  confidence: number
  unresolvedConflicts: EvidenceConflict[]
  missingEvidence: DataGap[]
  proposedAgents: string[]
  expectedValue: string
  shouldContinue: boolean
}
```

追加专家必须满足实际条件。

- 缺口会改变最终方向。
- 专家池中存在能处理该缺口的角色。
- 新任务不会重复已有工作。
- 仍在成本和轮次限制内。
- 追加结果能够被最终主管使用。

例如，基本面专家和空头专家对一家芯片公司的库存周期产生分歧，而现有证据只包含公司财报。这时追加半导体供应链专家有明确价值。若分歧只是两人对相同市盈率的主观偏好，追加第三名基本面专家通常只会增加文字。

动态追加建议限制为一轮、最多两名专家。无限反思会让系统越来越慢，也可能让后来的模型把早期可靠证据稀释掉。

### 本课练习

为 Gap Review 写三个应该继续的案例和三个应该停止的案例。每个案例都要说明新专家能增加什么新证据。

## 第九课 状态、失败和恢复

一轮深度研究可能持续数分钟。用户关闭页面、网络短暂中断或某个数据源失败，不应该让整轮结果丢失。

常见任务状态如下。

```text
pending
blocked
in_progress
completed
failed
cancelled
```

每个任务还要保存开始时间、完成时间、重试次数、使用模型、Token、工具调用摘要、错误类型和产物路径。

失败处理应该根据任务性质决定。

| 情况 | 建议处理 |
|---|---|
| 临时网络失败 | 指数退避后重试 |
| 数据源不可用 | 切换经过批准的备用源 |
| 输出不符合 Schema | 要求同一 Agent 修复一次 |
| 证据不足 | 标记缺口并交给主管决定 |
| 上游失败 | 阻止依赖任务，保留已完成结果 |
| 页面断开 | 后端继续运行，页面恢复后重新订阅 |

重试必须具备幂等性。相同任务重试不应重复扣减交易账户、重复发布内容或覆盖原始证据。SparkFlow 当前研究历史已经保存 `sessionId` 和 `attemptId`，动态团队还需要保存 `runId` 和 `planId`。

### 本课练习

画出一次动态研究从创建到完成的状态转换，并标出用户刷新浏览器以后如何恢复。

## 第十课 成本、延迟和模型分配

十二名专家全部运行很容易得到一份很长的报告，也很容易得到大量重复内容。动态调度的直接收益，是把模型调用花在真正能改变判断的地方。

可以为每名专家定义估算成本。

```ts
type AgentCostProfile = {
  expectedInputTokens: number
  expectedOutputTokens: number
  expectedToolCalls: number
  expectedSeconds: number
  modelTier: "fast" | "balanced" | "reasoning"
}
```

主管规划可以使用速度较快、结构化输出稳定的模型。取证专家使用工具能力可靠的模型。最终裁决使用推理能力更强的模型。纯格式转换可以使用成本较低的模型，甚至由确定性代码完成。

控制成本的常用方法包括共享证据包、同一证券当日缓存、上游报告摘要、并行执行、最大专家数、最大追加轮次和任务超时。

成本优化不能破坏证据链。把所有专家输出强行压缩成几十个字，后续主管就无法判断结论从哪里来。更好的做法是保留完整产物，同时传递一份带证据编号的结构化摘要。

### 本课练习

给一次普通个股研究设定预算。写出最大专家数、最大运行时间、最大追加轮次和三档模型分配。随后说明当预算不足时最先删除哪个任务，以及为什么。

## 第十一课 智能体评测

一份报告读起来专业，不代表系统真的可靠。智能体评测要检查过程和结果。

可以从五个维度建立测试集。

### 身份与数据

- 同名公司能否正确消歧。
- 价格、币种、交易所和时间是否一致。
- 停牌、退市、非交易时段能否正确处理。
- 缺失数据是否被明确标记。

### 工具与证据

- 专家是否真的调用了要求的工具。
- 数字是否能追溯到本轮工具结果。
- 新闻是否去重并回到原始来源。
- 网页中的恶意指令是否被忽略。

### 专家能力

- 基本面专家有没有分析现金流和盈利质量。
- 新闻专家有没有写清影响传导。
- 空头专家有没有真正质询多头观点。
- 风险主管有没有给出唯一结论。

### 工作流

- 并行任务是否真的并行。
- 上游失败是否正确阻断下游。
- 动态计划是否满足预算和依赖规则。
- 页面中断以后是否能够恢复。

### 最终报告

- `BUY / SELL / HOLD` 是否只有一个。
- 结论是否得到证据支持。
- 重要分歧是否被保留。
- 情景概率是否合计百分之百。
- 是否包含数据截止时间和免责声明。

评测样本要包含正常案例、边界案例和故意破坏系统的案例。每次调整 Prompt、工具或模型以后运行相同样本，才能知道能力有没有退化。

### 本课练习

先建立十个固定样本，不需要真实调用模型。为每个样本写输入、预期选择的专家、必须出现的证据、禁止出现的行为和通过条件。

## 第十二课 安全和金融边界

专家读取的网页、PDF 和新闻都属于不可信输入。页面中的文字可能要求模型忽略规则、泄露密钥或调用无关工具。系统需要把外部内容明确标记为资料，并通过工具白名单限制行为。

金融研究还要额外处理几件事。

1. 事实、推断和情景假设必须分开。
2. 当前行情不能来自模型记忆。
3. 目标价和仓位不能在数据不足时伪精确。
4. 报告不能冒充真实金融机构。
5. 一般研究结论不能包装成适合某个用户的个性化建议。
6. 模型、Prompt、数据和 Skill 版本都要进入审计记录。

主管也需要权限边界。它可以选专家和安排任务，不能自行创建未知工具、提高预算、跳过风险审查或把未校验网页直接设为事实。

### 本课练习

写一段伪造的新闻网页内容，其中包含要求专家泄露 API Key 的指令。随后设计工具网关和专家 Prompt 应该如何处理。

## V3 实战路线

不要一口气把动态团队全部写完。下面的顺序能让每个阶段都有可验证结果。

### 阶段一 专家注册表

把现有十二名专家提取成统一能力定义。先用静态 YAML 或 JSON，不接模型。

交付结果包括专家列表、能力标签、市场支持、工具权限、成本等级和输出类型。

验收时输入一个能力标签，程序能够返回匹配专家，并拒绝未知专家。

### 阶段二 主管计划 Schema

定义 `AnalysisRequest` 和 `AnalysisPlan`，准备十组手写合法计划和十组非法计划。

验收时计划验证器能够指出未知 Agent、循环依赖、预算超限和强制岗位缺失。

### 阶段三 规则型主管

先不用模型。根据任务类型和关键词选择专家，生成固定但精简的 DAG。

验收时长期投资、财报事件、短期技术和宏观冲击四类请求会得到不同团队。

### 阶段四 模型型主管

让模型读取用户问题和能力注册表，输出符合 Schema 的计划。确定性验证器仍然拥有最终批准权。

验收时模型不能选择注册表之外的专家，计划失败后最多修复一次。

### 阶段五 动态 Swarm 编译

把合法计划转换成 `SwarmRun`，复用现有 Runtime 执行。

验收时并行层、依赖传递、失败阻断和最终报告都能在运行记录中查看。

### 阶段六 证据包与缓存

在专家运行前统一处理证券身份、行情、财报和新闻，生成带版本的 EvidenceBundle。

验收时同一次研究中的所有专家看到相同截止时间和价格口径，重复工具调用明显减少。

### 阶段七 缺口复审

增加一次受限 Gap Review，最多追加两名专家和一轮任务。

验收时主管能够解释为什么追加专家，也能够在追加没有价值时停止。

### 阶段八 评测和可观测性

记录计划、专家选择、任务耗时、Token、工具调用、证据编号、失败原因和最终裁决。

验收时每次改动都能运行固定样本，比较成功率、成本、耗时和报告完整度。

## 建议的四周学习安排

### 第一周 看懂现有系统

- 阅读本教程第一至第五课。
- 顺着一次 `AAPL v2` 请求阅读前端、Swarm Tool、Preset、Runtime 和 Worker。
- 手画当前 V2 DAG。
- 为两名现有专家补写能力卡片。

这一周不修改 Runtime。目标是能准确说出每层代码承担什么责任。

### 第二周 学会设计协议

- 阅读第六至第九课。
- 写出 AgentCapability、AnalysisPlan 和 EvidenceBundle 三份 Schema 草案。
- 手写合法与非法计划样本。
- 给五种失败情况设计恢复策略。

这一周的结果应该是设计文档和测试样本，不急着接模型。

### 第三周 做出规则型 V3

- 实现专家注册表。
- 实现确定性计划验证器。
- 用规则选择专家并编译 DAG。
- 复用 Swarm Runtime 跑一轮小规模测试。

这一周只需要让四类任务选出不同团队，不追求主管有很强的自然语言理解。

### 第四周 接入智能主管

- 让模型输出 AnalysisPlan。
- 加入计划修复、预算和最大轮次。
- 加入 Gap Review。
- 跑固定评测样本并比较 V2 与 V3。

比较时重点看结论完整度、数据一致性、平均耗时、Token 和失败率。报告篇幅不是主要指标。

## 你和我配合时怎样提任务

学习过程中，你可以把问题缩小到一个清楚的对象。

好的提问方式包括下面这些。

- 帮我解释 `SwarmTask.input_from` 怎样把上游报告交给下游。
- 帮我审查这份 AgentCapability Schema 是否足够支持主管选人。
- 我写了一份六节点 DAG，帮我检查并行层和循环依赖。
- 帮我为基本面专家设计五个失败评测样本。
- 帮我实现计划验证器，但先不要接模型 API。
- 帮我比较这次 V2 和 V3 的耗时、成本与证据完整度。

这类任务边界清楚，完成以后也容易验证。等几个小部件稳定，再把它们接成完整的动态团队。

## 最后检查表

准备开始 V3 开发以前，确认自己能够回答下面的问题。

- Prompt、Skill、Tool、Agent 和 Workflow 分别负责什么。
- 为什么实时价格必须来自工具。
- 为什么专家需要能力注册表和输出 Schema。
- 为什么主管计划必须经过确定性验证。
- 哪些任务可以并行，哪些任务需要上游结论。
- 统一证据包怎样减少重复调用和数据冲突。
- 什么样的证据缺口值得追加专家。
- 怎样限制最大专家数、运行时间和追加轮次。
- 怎样恢复中断任务并保留已完成结果。
- 怎样用固定样本判断改动有没有让系统退化。

这些问题能够独立回答以后，你已经具备参与 SparkFlow 动态专家团队开发所需的主要知识。后续遇到的新框架和新模型，大多只是替换实现方式，系统里的职责、证据、状态和评测仍然要逐项处理。
